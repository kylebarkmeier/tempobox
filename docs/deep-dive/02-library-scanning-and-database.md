# Deep dive 2: Library scanning & the database

> Prerequisites: [Android primer](../android-primer.md) §4 (permissions), §7
> (Room).

TempoBox is local-first: the user's audio files on disk are the real data, and
the SQLite database is a **rebuildable index** of them plus a thin layer of
library-managed state (ratings, play counts, date-added) that exists *only* in
the database. Everything in this subsystem follows from that split.

## 1. The schema: one real table, everything else derived

[`TrackEntity`](../../core/database/src/main/kotlin/com/tempobox/database/entity/TrackEntity.kt)
is the `tracks` table — one row per audio file. Columns fall into two classes:

- **File/tag metadata** (title, artist, albumArtist, album, genre, year,
  track/disc number, duration, format, bitrate, size, mtime,
  `hasEmbeddedArt`) — owned by the file; a rescan may overwrite them.
- **Library-managed data** (`id`, `rating`, `playCount`, `dateAddedMs`) —
  owned by the database; a rescan must never touch them.

`filePath` has a unique index: the path is the natural key the scanner diffs
and upserts by, while the autogenerated `id` is the stable surrogate key
everything else (playlists, the queue snapshot) references.

The domain model
[`Track`](../../core/model/src/main/kotlin/com/tempobox/model/Track.kt) maps
1:1 (mapper functions `toModel()`/`toEntity()` live next to the entity) and
adds the display fallbacks: `effectiveAlbumArtist` (albumArtist → artist →
`"Unknown Artist"`), `effectiveAlbum`, `effectiveGenre`.

### Playlists

Two more tables
([`PlaylistEntities.kt`](../../core/database/src/main/kotlin/com/tempobox/database/entity/PlaylistEntities.kt)):
`playlists` (a static playlist mirrors an `.m3u8` file at `filePath`; a smart
playlist stores its rule tree as JSON in `smartRuleJson`) and
`playlist_entries` (ordered membership for static playlists, with
`ON DELETE CASCADE` foreign keys to both parents, so deleting a playlist or
removing a track from the library cleans entries up in SQL). Covered fully in
[deep dive 6](06-playlists.md).

## 2. Aggregates are queries, not tables

There is no `albums` table, no `artists` table, no `genres` table. The
Albums/Artists/Genres browse views are `GROUP BY` projections over `tracks`,
written as live Room queries in
[`TrackDao`](../../core/database/src/main/kotlin/com/tempobox/database/dao/TrackDao.kt):

```sql
SELECT album AS name,
       albumArtist AS albumArtist,
       MAX(year) AS year,
       COUNT(*) AS trackCount,
       SUM(durationMs) AS durationMs,
       MIN(CASE WHEN hasEmbeddedArt THEN filePath ELSE NULL END) AS artworkTrackPath,
       ...
FROM tracks
GROUP BY album, albumArtist
```

**Why.** Materialized album/artist rows would need synchronizing on every
scan, tag edit, and deletion — a whole class of consistency bugs. As pure
projections there is *nothing to keep in sync*: edit a genre tag and the
Genres tab, the artist's genre chips, and every smart playlist that matches on
genre are all correct on the next emission, because they're all reading the
same table. The cost is recomputing a `GROUP BY` on change, which SQLite does
in milliseconds at this scale (the table is indexed on `albumArtist`,
`album`, `genre`, `dateAddedMs`).

Details worth noticing in the DAO:

- Rows land in plain projection POJOs
  ([`AggregateRows.kt`](../../core/database/src/main/kotlin/com/tempobox/database/pojo/AggregateRows.kt)) —
  Room maps columns to fields by alias name.
- Artist rows need *lists* (genres, up to 4 artwork paths for the collage),
  which SQL can't return. The query `GROUP_CONCAT(..., CHAR(31))`s them with
  the ASCII unit separator — a character that can't appear in genres or file
  paths — and the mapper splits/dedups in Kotlin, because SQLite's
  `GROUP_CONCAT` can't combine `DISTINCT` with a custom separator.
- Blank tags are normalized *inside the SQL* (`CASE WHEN genre = '' THEN
  'Unknown Genre' …`) so grouping and filtering agree with the Kotlin-side
  `Track.effectiveGenre`; a DAO comment pins the two together.
- There are two artist aggregations: by `albumArtist` (the Album Artists tab)
  and by *track* artist with an albumArtist fallback (the Artists tab) —
  same shape, different `GROUP BY` key.

One deliberate oddity: **final sorting happens in Kotlin, not SQL**.
[`LibraryRepository`](../../core/library/src/main/kotlin/com/tempobox/library/LibraryRepository.kt)
applies comparators built from
[`SortSpec`](../../core/model/src/main/kotlin/com/tempobox/model/Sorting.kt),
because the product wants article-aware alphabetical order ("The Beatles"
under B — `sortNormalized()`), which SQLite collations can't express cleanly.
Tens of thousands of rows sort in single-digit milliseconds, so the trade is
free in practice.

## 3. The scanner: diff, don't re-read

[`MediaScanner.scan`](../../core/library/src/main/kotlin/com/tempobox/library/MediaScanner.kt)
is a four-step pipeline, guarded by a `Mutex` so overlapping triggers
(startup rescan + a watcher event) queue instead of racing:

```
1. Walk the library locations        → every supported audio file on disk
   (honoring .nomedia folders)
2. Diff against the DB               → "changed" = new path, or mtime/size differ
   (one lightweight SELECT of          (TrackScanMeta projection)
    path/mtime/size per scan)
3. Read tags ONLY for changed files  → TagReader.readTrack (jaudiotagger)
4. upsertKeepingUserData + prune     → rows whose files vanished are deleted
```

The diff is the whole performance story: an unchanged 10k-track library
rescans as **one directory walk + one indexed query + zero tag reads**. Tag
parsing is the expensive step (jaudiotagger opens and parses each file), so
the scanner's unit tests assert the zero-extra-reads property directly by
counting reads on a fake
([`MediaScannerTest`](../../core/library/src/test/kotlin/com/tempobox/library/MediaScannerTest.kt),
`` `unchanged files are not re-read on rescan (efficiency)` ``).

Other behaviors encoded there:

- `dateAddedMs` is preserved from the existing row for changed files (a
  retag isn't a re-add), set to `now` for new ones.
- Unparseable files are logged and *skipped*, never abort a scan
  (`TagReader.readTrack` returns null by contract).
- Deletions are chunked (`DELETE … WHERE filePath IN (…)` in batches of 500)
  because SQLite caps bound variables at 999.
- Progress streams out via a `StateFlow<ScanState>`
  ([`ScanState`](../../core/library/src/main/kotlin/com/tempobox/library/ScanState.kt):
  `Idle` / `Scanning(scanned, total)` / `Done(added, updated, removed)`), which
  Settings renders live.

There's also `scanPaths(paths)` — an incremental variant the file watcher
feeds with just the changed paths, skipping the directory walk entirely.

## 4. `upsertKeepingUserData`: the rescan-safety contract

The invariant "rescans never lose user data" is implemented in exactly one
place, as a Room `@Transaction` in
[`TrackDao`](../../core/database/src/main/kotlin/com/tempobox/database/dao/TrackDao.kt):

```kotlin
@Transaction
suspend fun upsertKeepingUserData(entities: List<TrackEntity>) {
    for (entity in entities) {
        val existing = getByPath(entity.filePath)
        if (existing == null) {
            insert(entity)
        } else {
            update(entity.copy(
                id = existing.id,
                rating = existing.rating,
                playCount = existing.playCount,
                dateAddedMs = existing.dateAddedMs,
            ))
        }
    }
}
```

Freshly-read tag metadata wins; identity and the four library-managed columns
are carried over from the existing row. Because it's the *DAO* that enforces
this, every caller gets the guarantee for free — the scanner, the watcher's
incremental path, and crucially also the tag editor
([deep dive 9](09-tags-and-editing.md)), which re-syncs DB rows after writing
files and must not reset your ratings in the process.

It's a read-then-write loop rather than a single SQL `UPSERT`; `@Transaction`
makes it atomic and keeps SQLite fast enough (one indexed point-read per
changed file, and only changed files ever reach this function).

## 5. The lifecycle wiring: `LibraryInitializer`

[`LibraryInitializer.onAppStart`](../../core/library/src/main/kotlin/com/tempobox/library/LibraryInitializer.kt)
(called from `TempoBoxApplication.onCreate`) launches three independent
process-lifetime jobs on the `@ApplicationScope`:

1. **Startup rescan** — if `library.autoRescanAndWatch` (default ON) and
   locations are configured: `scanner.scan(locations)` then
   `playlistRepository.importPlaylistFiles(locations)` (`.m3u`/`.m3u8` files
   found in the library become playlists automatically).
2. **Watcher supervision** — observes the settings flow for changes to
   `(autoRescanAndWatch, locations)` (`distinctUntilChanged`), and
   restarts/stops the `LibraryWatcher` accordingly. Toggling the setting off
   genuinely stops the observers.
3. **Smart-playlist export refresh** — observes `trackDao.observeAll()`,
   reduces each emission to a cheap change signature
   (`rows.size to rows.sumOf { it.dateModifiedMs }`), drops the initial
   startup emission, samples at 5-second intervals, and calls
   `playlistRepository.refreshSmartExports()`. This is what keeps smart
   playlists' `.m3u8` files on disk in step with a changing library without
   rewriting them on every keystroke of a tag edit ([deep dive 6](06-playlists.md)).

`rescan()` (Settings ▸ "Rescan library") is the same scan+import pair,
on-demand.

## 6. Live folder watching: `LibraryWatcher`

[`LibraryWatcher`](../../core/library/src/main/kotlin/com/tempobox/library/LibraryWatcher.kt)
turns filesystem events into incremental scans. The constraints shape the
implementation:

- **inotify isn't recursive.** Android's `FileObserver` (a thin wrapper over
  Linux inotify) watches a single directory, so `start()` walks each library
  location and registers one observer per directory in the tree.
- **A new directory needs new watches.** When an event names a directory
  (e.g. the user copies a whole album folder in), the handler walks it,
  registers observers for its subtree, and queues every file inside it for
  scanning.
- **File copies are noisy.** A single copy emits bursts of
  `CLOSE_WRITE`/`MOVED_TO` events, so changed paths are collected into a set
  and `sample`d on a 2-second window before being handed to
  `MediaScanner.scanPaths` as one batch.
- The event mask is `CLOSE_WRITE | MOVED_TO | MOVED_FROM | DELETE | CREATE` —
  deliberately *not* `MODIFY`, which would fire per-write during a copy.

Combined effect: drop files into a watched folder and they appear in the
library a couple of seconds later, with no full rescan and no user action.

## 7. Reads, mutations, and deletions: `LibraryRepository`

[`LibraryRepository`](../../core/library/src/main/kotlin/com/tempobox/library/LibraryRepository.kt)
is the UI-facing facade over the track table (playlists have their own
repository; scanning its own class). Beyond the observe/sort wrappers already
mentioned:

- `getTracksByIds(ids)` **preserves caller order** (the queue is rebuilt from
  an ordered id list on restore) and chunks the `IN (…)` query for the
  999-variable limit.
- `setRating` / `incrementPlayCount` update the two library-managed columns —
  note ratings live only in the DB, they are *not* written into file tags.
- `removeFromLibrary(trackIds)` deletes rows only; files stay on disk (the
  next rescan of a still-watched folder would re-add them — "remove" is
  meant for pruning stale entries, and the UI words it accordingly).
- `deleteFromDevice(trackIds)` partitions into deleted/failed by actually
  attempting `File.delete()`, removes rows **only for files that really went
  away**, and returns the failures so the UI can point the user at the
  All-files-access grant ([primer §4](../android-primer.md)). A failure mode
  is a return value here, not an exception — bulk operations must finish the
  rest of the batch.
- `editTags` is the tag-editing write path — covered in
  [deep dive 9](09-tags-and-editing.md), but note it ends in the same
  `upsertKeepingUserData`.

## 8. Testing posture

Everything above tests on the JVM, no emulator:

- DAOs and the scanner run under **Robolectric** (a JVM implementation of the
  Android runtime) against **in-memory Room** databases — see
  [`TrackDaoTest`](../../core/database/src/test/kotlin/com/tempobox/database/TrackDaoTest.kt)
  and [`MediaScannerTest`](../../core/library/src/test/kotlin/com/tempobox/library/MediaScannerTest.kt).
  Each such module pins `sdk=35` in `src/test/resources/robolectric.properties`
  because Robolectric 4.14 doesn't support SDK 37 (the compileSdk) yet — an
  easy thing to trip over when bumping compileSdk.
- Tag IO is faked by
  [`FakeTagIO`](../../core/library/src/test/kotlin/com/tempobox/library/Fakes.kt),
  which derives "tags" from the file name (`Artist__Album__Title.mp3`), so
  tests control metadata by naming temp files — no real audio fixtures
  anywhere in the scanner/repository suites. (jaudiotagger's actual
  byte-level parsing is a documented deliberate test gap, covered manually.)
